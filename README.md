# Secrethon2026

MCP-сервер: [підключення локальних і віддалених агентів](backend/MCP.md).

## AI-агент

Панель агента використовує `POST /api/agent/chat`: Gemini обирає визначені інструменти
читання PostgreSQL, Tavily шукає публічні згадки. Таблиці та графіки створюються на
бекенді з результатів SQL, з датою зрізу й джерелами. Діалог передає контекст сторінки
та останні 12 повідомлень; історія зберігається в пам’яті поточної вкладки.
Кнопка «Новий чат» у шапці панелі очищає діалог, історію та незавершений вибір
джерел, скасовує поточний запит і залишає збережені дослідження доступними.

Перед потрібним вебпошуком агент показує в чаті «Шукати в базі» та «Шукати в базі та інтернеті».
До вибору Tavily не викликається. Дозвіл діє лише для поточного питання; нове питання
знову потребує дозволу, якщо модель планує вебпошук. Вибір «Шукати в базі»
блокує вебінструмент на сервері, зокрема при повторі після помилки.
API-поле `web_access`: `ask` за замовчуванням, `allowed` після явного вибору,
`db_only` після відмови. Відповідь з `web_permission` означає паузу перед пошуком;
клієнт повторює початкове питання з тим самим контекстом та обраною політикою.
Прямий виклик MCP `search_mentions` залишається явним запитом вебпошуку.

На карті можна обрати контекст підприємства, видимої області, поточних фільтрів
або до п'яти компаній для порівняння. Межі області фіксуються при надсиланні.
Сервер рахує всю вибірку, а рейтинги обмежені й позначені як часткові.
Відповіді розділені на дані платформи, матеріали відкритих джерел і висновок агента.
Дії відповіді відкривають підприємства або відомі зв'язки на карті.
Запит про конкретне підприємство на карті автоматично наближає його адреси з реєстру й місця найму.
Запит про зв'язки відкриває мережу саме знайденого підприємства. ID перевіряється
бекендом; режим мережі має пріоритет над помилковим звичайним наближенням моделі.
Мережа включає постачання, холдинги та прямі записи про пов'язані компанії, банки,
правонаступництво й філії. Загальна пов'язаність не позначається як постачання чи власність.
Лінії доступні також у резервній карті OpenStreetMap; компанії без координат показано в переліку.
Неоднозначна назва потребує уточнення. Згадка установи в описі іншої
картки позначається як зв'язок, а не тотожність. Якщо користувач перейшов на іншу
сторінку під час відповіді, автоматичне переміщення не виконується.

«Переглянути перед збереженням» відкриває ручний апрув. Після підтвердження
переглянута версія, джерела й використані дані зберігаються в `localStorage`
на цьому пристрої. Кнопка «Збережені дослідження» в шапці чату дозволяє відновити, експортувати,
створити нову схвалену версію або видалити дослідження. Чернетки автоматично
не зберігаються. Схвалення не підтверджує автоматично вебматеріали.
План наступних етапів: [покращення агента](backend/AGENT_IMPROVEMENTS.md).

У кореневому `.env`, `backend/.env` або Railway Variables задайте `GEMINI_API_KEY`, `TAVILY_API_KEY`,
`GEMINI_MODEL` (за замовчуванням `gemini-3.5-flash-lite`). Ключі використовуються лише
сервером. `AGENT_ENABLED=false` вимикає агента; `/api/agent/status` показує готовність
конфігурації без секретів. Значення з `backend/.env` перекривають кореневий `.env`,
а змінні середовища мають найвищий пріоритет. Після зміни змінних перезапустіть бекенд.

Підтримуються профілі, санкції, зв’язки, вакансії, порівняння, рейтинги й аналітика
за підприємством, регіоном, напрямом та місяцем. Період БД відраховується від дати
зрізу. Динаміка показує **активні вакансії за місяцем публікації**, а не історичну
чисельність вакансій. Зарплати — медіани відомих місячних зарплат у RUB. Пошук Tavily
показує кандидатів на згадки, не гарантує повноти соцмереж і підтвердження заяв.
Відео не обробляється.

Бекенд обмежує одну відповідь 12 раундами моделі, 18 викликами інструментів і 2
пошуками Tavily. Є ліміт 6 запитів на хвилину з IP та 2 одночасних аналізи на процес.
Виклики витрачають квоту провайдерів; окремої авторизації агента поки немає.

.venv/Scripts/python.exe scripts/smoke_agent_map.py

# Жива перевірка Gemini: запит дозволу без запуску Tavily.

## Локальная разработка

Нужны Node 22+, [uv](https://docs.astral.sh/uv/) и Docker (для тестовой базы).

```bash
# Бэкенд → http://localhost:8000 (документация API: /docs)
cd backend
cp .env.example .env      # и впишите DATABASE_URL базы с данными (см. «База данных»)
uv sync
uv run uvicorn app.main:app --reload

# Фронтенд → http://localhost:5173 (запросы /api проксируются на :8000)
cd frontend
npm install
npm run dev
```

Проверки (те же, что в CI):

```bash
docker compose up -d      # Postgres для тестов → localhost:5432
cd backend && uv run ruff check . && uv run ruff format --check . && uv run pytest
cd frontend && npm run lint && npm run build
```

Новые эндпоинты добавляйте в `backend/app/api/` и подключайте в `app/api/__init__.py`, чтобы они были под префиксом `/api`. SQL живёт в `backend/app/repository/`. Всё остальное отдаётся как SPA (`index.html`).

## Карта 2ГІС

Карта використовує MapGL JS API 2ГІС та офіційний плагін кластеризації.
Вона доступна в `/map`, на сторінці регіону та у вкладці «На карті» профілю.
Фільтри регіону й напряму обмежують роботодавців на карті.
Пошук у списку фільтрує карту за назвою, містом, регіоном або ІПН.
Натискання на позначку відкриває картку роботодавця, на кластер — наближає карту.
Доступні 2D/3D, масштабування, повний екран, показ усієї вибірки та фільтр санкцій.

Налаштування локально:

1. Скопіюйте `frontend/.env.example` у `frontend/.env`.
2. Вкажіть `VITE_2GIS_API_KEY` — ключ із доступом до **Map Tiles API**.
3. Перезапустіть Vite. Без ключа показується повідомлення про налаштування;
   список роботодавців залишається доступним.

На Railway задайте `VITE_2GIS_API_KEY` у Variables сервісу і перебудуйте образ.
Dockerfile приймає однойменний аргумент збірки. Для ручної збірки:

```bash
docker build --build-arg VITE_2GIS_API_KEY=your_browser_key -t secrethon2026 .
```

Ключ вбудовується у фронтенд під час збірки і є видимим у браузері.
Налаштуйте дозволені домени у кабінеті 2ГІС.
Документація: https://docs.2gis.com/en/mapgl/start/first-steps.

`GET /api/employers/map-points` читає координати з активних вакансій,
класифікованих останнім запуском як `confirmed` або `likely`.
Вакансії групуються за роботодавцем і парою `lat/lng`; кілька місць найму
одного роботодавця зберігаються. Відсутні або некоректні координати не
відображаються. Геокодування назв міст і вигаданих координат немає.
Це місця найму за даними джерел, а не перевірені адреси підприємств.
Лічильник на карті показує покриття координатами поточної вибірки.

У панелі «Шари карти» незалежно вмикаються мітки, ланцюги постачання,
зв’язки холдингів та щільність вакансій. Теплова карта зважена за кількістю
активних ВПК-вакансій у кожній точці. Фільтри санкцій і спеціалізації
(БПЛА, озброєння та компоненти) застосовуються до всіх шарів разом із
пошуком, регіоном і напрямом.

`GET /api/employers/map-network` читає `company_edge` (типи `supplier`
і `parent`) з назвами, джерелами, описом постачання та посиланнями,
а спеціалізацію — із `company_uav_model`, `company_weapon` і
`company_weapon_component`. Напрям стрілки: постачальник → замовник
або материнська → дочірня компанія. Компанії зіставляються з роботодавцями
за ІПН; для кінця лінії обирається місце найму з найбільшою кількістю
вакансій у поточній вибірці. Це зв’язки між компаніями, а не маршрути
перевезень чи підтверджені адреси заводів. Без координат обох компаній
лінія не малюється. Зв’язки зі спільними координатами доступні в переліку.

## Рейтинг важливості

`/rating` показує рейтинг підприємств ВПК за важливістю: частку випуску БпЛА, ракет і КАБ,
що залежить від підприємства (методика — у `company-parse/docs/rating_methodology.md`).
Рейтинг рахує пайплайн (`classifier_run` `importance_rating`, таблиці `company_rating`,
`rating_unit`); сайт лише читає останній прогін і кешує його на 3 хвилини.
Вкладки: підприємства (з розкладом балу), галузі, регіони, холдинги, системи та ваги,
перевірка, слабкі місця, методика. На картці підприємства — «Місце в рейтингу»,
«Фінанси» (ГІР БО) і вкладка «Ланцюг постачання». Юрособа без вакансій відкривається
як `/enterprises/{company_id}`.

API: `GET /api/rating` (`focus`, `tier`, `domain`, `region`, `q`, `limit`, `offset`),
`/api/rating/meta`, `/api/rating/units?kind=domain|region|holding`,
`/api/rating/{company_id}`, `GET /api/enterprises/{company_id}`. Агент і MCP мають
інструмент `rating`.

## Профілі вакансій і перевірки

Вакансія відкривається окремою сторінкою `/vacancies/:id`. У профілі є
опис, зарплата, місце найму, посилання на підприємство й оригінал оголошення.
На вкладці «Зв’язки» підприємства показаний граф прямих зв’язків із фільтрами
за типом, масштабуванням і переходами до наявних профілів.

Human review та LLM review зберігаються незалежно в
`web_reviews.vacancy_review`. Кожен запис містить `source` (`human` або `llm`),
`confidence` (`high`, `medium`, `low` — ймовірність дотичності до ВПК),
`reviewed_by` (ім’я/позивний для людини, ідентифікатор моделі для LLM),
коментар і серверну дату. Ім’я вводиться автором; авторизації користувачів
поки немає. Нові перевірки додаються до історії, остання оцінка кожного типу
показується окремою міткою. Класифікація пайплайна й статистика не змінюються.

`POST /api/vacancies/:id/reviews` приймає ці поля; інтерфейс надсилає тільки
ручні перевірки. Майбутній LLM-пайплайн надсилає `source: "llm"` і назву
реальної моделі. Поточні `hh_filter` і `trudvsem_vpk_rules` показуються
окремо й не видаються за LLM review. Дані та історію повертає
`GET /api/vacancies/:id`.

### Human review підприємства

На картці підприємства (`/companies/:id`) у правій колонці є розділ «Human review»:
аналітик може вручну задати кожну категорію з шапки картки — джерело інформації
(`sources`: hh, trudvsem, superjob, gur, registry, company_site, media, other),
надійність джерела за шкалою Адміралтейства (`reliability`: A–F), напрям
діяльності (`category`: производство, НИИ/КБ, ремонт), санкції (`sanctions`:
sanctioned, not_sanctioned) і дотичність до ВПК (`vpk`: confirmed, likely, no).
Незаповнене поле означає «лишити автоматичне значення».

Ревізії зберігаються append-only у `web_reviews.employer_review`; діє остання.
Кожна ревізія — повний знімок рішень людини з автором, коментарем і датою.
Остання ревізія перекриває автоматичні значення на картці, у списку
підприємств (фільтр напряму, ознаки, сортування за санкціями), на карті та
повертається як `human_review` у `GET /api/employers` і `GET /api/employers/:id`
(там же історія `human_reviews`). Агент і MCP бачать її через ці ж відповіді.
У відкритих даних датасет `employers` має колонки `human_*`; автоматичні
колонки (`category`, `sanctions_count`, …) лишаються як зібрані.
Нова ревізія: `POST /api/employers/:id/reviews`.

Читання бази пайплайна залишається в транзакціях лише для читання.
Окреме з’єднання створює схему/таблицю перевірок під час першого явного
збереження, тому користувач БД має мати дозвіл `CREATE` в цій базі.
Перевірки спільні для всіх користувачів, зберігаються після перезапуску
і не залежать від локального сховища браузера. Телефон, email і ПІБ контактної
особи не зібрані в поточній схемі; «Коротко» відображає це явно, а ОДРН і КПП
бере з наявних записів роботодавця/ГУР.

## База данных

PostgreSQL, SQLAlchemy 2.0 (async, asyncpg), миграции через Alembic. Строка подключения всегда берётся из `DATABASE_URL`:

| Где | Откуда `DATABASE_URL` |
|---|---|
| Локально | `backend/.env` (копия `.env.example`, указывает на Postgres из `docker-compose.yml`) |
| Railway | переменная сервиса `DATABASE_URL=${{Postgres.DATABASE_URL}}`, приватная сеть Railway |
| CI | Postgres в service container GitHub Actions |

`.env` в git не коммитится. Каждый разработчик работает со своей локальной базой, а не с продовой.

Изменили модели в `backend/app/models.py`? Создайте миграцию и закоммитьте её:

```bash
cd backend
uv run alembic revision --autogenerate -m "add users"   # проверьте сгенерированный файл
uv run alembic upgrade head
```

CI проверяет (`alembic check`), что модели и миграции совпадают. На Railway миграции применяются автоматически перед каждым деплоем (`preDeployCommand` в `railway.json`). Если миграция упала, деплой не переключится.

### Данные

Основные таблицы пайплайна: `company`, `employer_profile`, `vacancy`, `vacancy_classification`, `company_edge`. Чтение: `GET /api/employers`, `/api/employers/{id}`, `/api/vacancies?employer_id=`, `/api/vacancies/{id}`, `/api/stats`. Сохранение независимых проверок: `POST /api/vacancies/{id}/reviews`, только в схему `web_reviews`.

Приложение читает данные сбора из PostgreSQL; снимок схемы пайплайна хранится в `backend/db/schema.sql`. Искусственные данные из `backend/tests/fixtures/sample.sql` используются только в изолированной локальной тестовой базе.

Галузь і роль вакансії читаються з окремого прогону JEV (`vacancy_direction_latest`), а рішення про належність підприємства до ВПК залишається з пайплайна. Перед запуском оновленого бекенду на іншій БД застосуйте `backend/db/vacancy_directions.sql`. [Повний прогін для активних вакансій ВПК, імпорт та відкат](backend/JEV_LABELING.md) описані окремо; звичайні запити застосунку залишаються лише для читання.

Фронт грузит весь датасет один раз (`frontend/src/data/load.ts`) и фильтрует на клиенте. Относительные даты («2 дні тому») и фильтр периода считаются от самой свежей записи в данных, а не от текущего времени.

Заглянуть в продовую базу: Railway → Postgres → вкладка **Data**, либо `railway connect Postgres` через [Railway CLI](https://docs.railway.com/guides/cli).

## CI/CD

- **CI** (GitHub Actions, на каждый PR и пуш в `main`): ruff, проверка миграций и pytest на Postgres для бэка, oxlint и сборка с typecheck для фронта, сборка Docker-образа со smoke-тестом.
- **CD** (Railway auto-deploy): Railway сам собирает `Dockerfile` при пуше в `main`, применяет миграции и проверяет `/api/health` (включая соединение с БД) перед переключением трафика.

### Настройка Railway (один раз)

1. Railway → **New Project → Deploy from GitHub repo** → выбрать этот репозиторий.
2. Settings сервиса:
   - **Root Directory**: пусто (корень репо). Конфиг подтянется из `railway.json`.
   - **Source → Branch**: `main`.
   - **Wait for CI**: включить, чтобы деплой шёл только после зелёного CI.
3. **Networking → Generate Domain**, чтобы получить публичный URL.
4. **+ New → Database → PostgreSQL**, затем в Variables сервиса приложения добавить `DATABASE_URL` = `${{Postgres.DATABASE_URL}}`.

Переменные окружения задаются в Railway → Variables. `PORT` Railway подставляет сам.
