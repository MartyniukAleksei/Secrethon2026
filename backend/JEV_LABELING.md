# Розмітка вакансій через JEV

Скрипт `scripts/classify_vacancies.py` читає вакансії через з’єднання PostgreSQL з `default_transaction_read_only=on`, звертається до офіційного API JEV і зберігає результати лише у локальні файли. Він не має режиму запису в БД. Розмітка не змінює діаграми сайту.

## Повна класифікація вакансій ВПК та публікація в БД

Для явного імпорту використовуються окремі скрипти. З папки `backend`:

```powershell
.venv\Scripts\python.exe scripts/classify_vacancies.py --all --export-only --output ../reports/jev-all
.venv\Scripts\python.exe scripts/apply_vacancy_directions.py --prepare --source ../reports/jev-all
.venv\Scripts\python.exe scripts/export_vpk_inputs.py --source ../reports/jev-all --output ../reports/jev-vpk
.venv\Scripts\python.exe -u scripts/classify_all_vacancies.py --output ../reports/jev-vpk --cache-dirs ../reports/jev-all ../reports/jev-alabuga-full ../reports/jev-vacancy-pilot --concurrency 32
.venv\Scripts\python.exe scripts/apply_vacancy_directions.py --apply --source ../reports/jev-vpk
```

Сирий експорт читає узгоджений snapshot усіх записів лише для локального відбору. До JEV та імпорту в цьому сценарії потрапляють **лише активні вакансії ВПК без дублів**: фінальна категорія `vpk`, рівень `confirmed` або `likely`. Відсіяні записи, неактивні вакансії та вакансії агенцій не входять у прогін. Обсяг поточної бази — 35 650 вакансій, а не 142 636 сирих записів. `export_vpk_inputs.py` звіряє ID з цим критерієм у БД.

Повний сирий експорт має окремий довший таймаут; звичайні запити сайту залишаються обмеженими. Якщо локальний експорт `jev-all/inputs.jsonl` уже існує, повторно скачувати його не потрібно. `--prepare` зберігає старі класифікації у стиснуті JSONL у `backups/` і створює таблиці зі схеми `db/vacancy_directions.sql`.

Повний прогін зберігає одну валідну відповідь на кожен fingerprint у `responses.jsonl`, поточний стан у `progress.json`, мітки всіх ID у `labels.jsonl`, а також CSV. Якщо його перервати, повторення команди використовує успішні відповіді. Помилки повторюються окремими проходами; невдалий результат не стає міткою. Паралелізм налаштовується від 1 до 32; при лімітах API його можна зменшити.

Імпорт вимагає 100% покриття вибраного обсягу, нуль помилок і відповідність міток сирим відповідям JEV. Перед записом він повторно звіряє поточні тексти вакансій з експортом та точний набір активних вакансій ВПК. Зміна текстів або набору ID зупиняє імпорт; зміни текстів записуються у `stale_inputs.json`.

Нові мітки зберігаються у `vacancy_direction`, історія прогонів — у `vacancy_direction_run`. Усі рядки та публікація записуються однією транзакцією. Перевірка підприємств на належність до ВПК (`vacancy_final`), класифікація підприємств і людські рев’ю не замінюються. Сайт та MCP-аналітика читають `vacancy_direction_latest`: галузь і роль вакансії; `none` не успадковує військову галузь роботодавця. Для ще не розмічених вакансій зберігається попереднє джерело підприємства.

`import_receipt.json` містить ID прогону, контрольну суму, кількість імпортованих міток і команду відкату. Відкат позначає прогін `withdrawn`; його рядки залишаються для аудиту, а сайт читає попередній опублікований прогін (або старе джерело підприємства).

Для іншої БД спочатку застосуйте `db/vacancy_directions.sql`; локальні тести встановлюють цю схему в ізольовану тестову БД. Звичайне з’єднання застосунку залишається лише для читання; імпорт використовує окреме з’єднання.

Ключ `JEV_API_KEY` задається у `backend/.env`, який виключено з Git. Модель визначає `JEV_MODEL` (типово `jev-latest`). Для повторення пілота можна вказати повернуту ним версію `jev-1.13.0`.

## Пілот

З папки `backend`:

```powershell
.venv\Scripts\python.exe scripts/classify_vacancies.py --company-ids 4064 3263 2054 5206 --per-company 40 --output ../reports/jev-vacancy-pilot
```

Це Алабуга, Роскосмос, СТЦ та Авіакор. ID Алабуги — **4064**, а не 406.

Вибірка включає одну вакансію на назву професії: 8 найчастіших назв і решту за відтворюваним хешем. Відсотки такого пілота не оцінюють усі вакансії компанії. Різні описи однакової професії не успадковують її мітку: кеш працює лише для однакових вхідних текстів, критеріїв, моделі й версії запитань.

## Повний прогін

Усі активні вакансії Алабуги без дублів, без обмеження за назвами професій:

```powershell
.venv\Scripts\python.exe scripts/classify_vacancies.py --company-ids 4064 --full-company --output ../reports/jev-alabuga-full
```

Скрипт звіряє кількість та унікальність експортованих ID з кількістю активних вакансій у БД. Неактивні записи не входять у цей режим. Частки повного прогону компанії рахуються за кількістю вакансій, а не назв професій.

Усі сирі записи всієї бази:

```powershell
.venv\Scripts\python.exe scripts/classify_vacancies.py --all --output ../reports/jev-all
```

Цей режим охоплює всі сирі записи, включно з неактивними та копіями, і також не записує в БД. `--limit 100` обмежує прогін. `--export-only` зберігає вхідні дані без звернень до API. Після переривання можна повторити команду з тією самою папкою: успішні рішення будуть взяті з кешу, помилки — повторені.

## Категорії та перевірка

Довідник кодів читається з `company_classification.direction_domain` (16 галузей) і `direction_role` (9 ролей діяльності). Невідомий код зупиняє запуск, щоб спочатку додати його зміст до критеріїв. `none` означає недостатність даних і не створює категорію в БД.

JEV класифікує обов’язки вакансії, а не підприємство. Будівництво, HR і загальне IT належать до наявної цивільної категорії; робота безпосередньо над БпЛА — до БпЛА. Наявність роботодавця у ВПК при цьому не переоцінюється. Роль діяльності визначається незалежно від галузі.

Рішення з `none` або confidence нижче 0,75 хоча б в одному вимірі позначаються для ручної перевірки. Confidence не є виміряною точністю, тому потрібна перевірка і частини впевнених рішень. Обмеження довжини полів записуються у звіт; email і телефони прибираються з вхідного тексту.

Папка результатів містить `index.html` з фільтрами й текстами вакансій, `REPORT.md`, `vacancies.csv`, `manifest.json`, `inputs.jsonl` і відповіді API у `results.jsonl`. Локальні `reports/jev-*` виключено з Git.

Схема запитів: [офіційна документація TypeSafe / JEV](https://docs.typesafe.ai/api).

## GPT as a judge

У `backend/.env` задаються `GPT_BASE_URL`, `GPT_MODEL=gpt-6-luna` та командний ключ `TEAM_KEY_GPT`. Також підтримуються назви `TEAM_API_KEY` і `GPT_API_KEY`. Ключ не передається JEV і не потрапляє в звіти.

```powershell
.venv\Scripts\python.exe scripts/review_jev_vacancies.py --source ../reports/jev-alabuga-full --output ../reports/jev-alabuga-gpt-review --concurrency 4
```

Скрипт не підключається до БД: читає збережений повний експорт Алабуги. GPT спочатку незалежно класифікує вакансію без міток і confidence JEV, а потім перевіряє кандидатні мітки. Обидва етапи виконуються для кожного різного тексту; повтори повного тексту мають спільну оцінку. Метрики рахуються окремо за всіма вакансіями й різними текстами.

Запити містять усі унікальні рядки оригіналу й незмінні визначення категорій; точні повтори рядків прибираються лише з запиту. Модель посилається на ID рядка, а точна цитата підставляється з оригіналу. Результати `supported`, `incorrect`, `ambiguous`, `insufficient` зберігаються окремо для галузі й ролі. Це оцінка моделі, а не виміряна точність на людському еталоні.

Успішні відповіді обох етапів зберігаються в `responses.jsonl`; повторний запуск з тією самою папкою використовує кеш. При обмеженні швидкості gateway повторює запити з довшими паузами. `--limit 10` запускає неповний пробний прогін за десятьма різними текстами. Папку результатів рев’ю потрібно тримати окремо від джерела JEV.
